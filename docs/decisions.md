| 2026-10-19 | The privacy guarantee covers the creator's signed-in account: it can never read purchase data through tables, RPC, Realtime or server actions. A creator who opens the public share link signed out sees what any guest sees; this is an accepted limit. | The share link is public by design; requiring guests to sign in adds friction and a creator could still use a second account. |
| 2026-10-19 | No client role can read the buyer's name or user id; guests only see "taken / not taken". Buyer identity moves to a `purchase_buyers` table with no policies and no client grants. | The UI never shows the buyer; storing identity where no client can read it is the smallest attack surface. |
| 2026-10-19 | Privacy fix goes before the provider spike. | The live audit confirmed buyer names are readable by every visitor (finding K). |
| 2026-10-19 | Production data is test-only, so the privacy fix needs no backfill and no staging project first. | 2026-10-19 | The creator-exclusion on `purchases` goes through a SECURITY DEFINER helper `is_wishlist_owner(wishlist_id)`, not a kept SELECT grant on `wishlists`/`items`. Policy: `purchases_select_non_owner` = `not is_wishlist_owner(wishlist_id)`. | It fails closed: anon has no privilege at all on `wishlists`/`items`, whereas a grant with zero policies silently reopens reads the day someone adds a policy. The helper only tells a caller whether they own a list. |
| 2026-10-19 | `reserve_item(p_item_id, p_buyer_name)` refuses the creator and an unknown item with one error (SQLSTATE 42501, "cannot reserve this item") before reading purchase status; a guest on a taken item gets 23505; a bad name gets 22023. The server action shows one generic message for everything except 23505. Parameters are `p_`-prefixed. | No status oracle for the creator; guests can already see that an item is taken. `p_` avoids plpgsql clashes with column names. |
| 2026-10-19 | `get_shared_wishlist(p_slug)` returns `jsonb` (`id`, `title`, `description`, `is_owner`, `items[]` with `taken`), `null` for an unknown slug, no `owner_id`; the page validates it with zod. | One round trip, `taken` is `null` for the creator, and the owner id never leaves the database. Trade-off: the payload is not covered by generated types. |
| 2026-10-19 | `wishlists`/`items` policies: one per command, `to authenticated`, owner only, with `WITH CHECK` on UPDATE. `anon` has no privilege on them. `purchases`: SELECT only for `anon` and `authenticated` (Realtime for guests); no write policy or grant. | Closes B, L and M; `WITH CHECK` stops ownership transfer and moving an item to another list. |
| 2026-10-19 | The migration copies buyers into `purchase_buyers` before dropping the old columns and aborts if a name is blank or the row counts differ. Existing `share_slug` values are regenerated, so the current share link changes. | No buyer is lost silently; the data is test-only so a new slug is acceptable (sprint 1 rules). |
| 2026-10-19 | `share_slug` default is `encode(extensions.gen_random_bytes(12), 'hex')` (96 bits), schema-qualified. | pgcrypto lives in `extensions` on Supabase and the default runs with the caller's `search_path`. |
| 2026-10-19 | `lib/supabase/database.types.ts` was hand-edited for task 3 (generator format) and must be regenerated later (backlog 30). Task 3 grid: 138 tests, proved on a local Postgres 16 with pgTAP; a mutation (status checked before the creator, EXECUTE granted to PUBLIC) makes the new tests fail. `supabase db reset` and `supabase test db` are verified only in CI. | `supabase gen types` needs Docker, which this session cannot run; the connector reads the unmigrated live schema. |
| 2026-10-19 | `UPDATE` on `items` and `wishlists` is granted per column to `authenticated` (items: `title`, `merchant_url`, `price`, `image_url`, `note`, `position`; wishlists: `title`, `description`); `INSERT`, `DELETE` and `SELECT` stay table-level. `id`, `wishlist_id`, `owner_id`, `share_slug` and the timestamps are not client-writable. `updated_at` still works: the `set_updated_at` trigger needs no column privilege. `position` is granted although the app does not write it yet. | A table-wide `UPDATE` let the creator PATCH `id`: `purchases_item_id_fkey` and `purchases_wishlist_id_fkey` (no `ON UPDATE CASCADE`) raise 23503 on a taken item or list and succeed on a free one, a purchase status oracle. It also let the creator change `items.wishlist_id`: moving a taken item to another of their lists and deleting the old list cascade-deletes the reservation through `purchases.wishlist_id`. Without the column privilege both fail with the same 42501. |
| 2026-10-19 | `20260709100000_privacy_fix.sql` was edited in place (no second migration) and keeps its explicit `begin`/`commit`. | The migration is not applied to any persistent database (owner statement; the connector could not be reached to re-check the live history). The file is destructive and relies on aborting cleanly, so it must be atomic whatever the apply path (CLI or MCP); removal would need evidence about both paths, which this session does not have. |
| 2026-10-19 | `supabase/tests/database/00_default_privileges.sql` is a functional probe: as the migration role it creates a scratch table and function in `public`, checks, one test per privilege, that `anon` and `authenticated` get SELECT, INSERT, UPDATE, DELETE and TRUNCATE on the table and EXECUTE on the function (and PUBLIC EXECUTE), then rolls back. A catalog check on `pg_default_acl` would only test the configuration, not the effect. |
